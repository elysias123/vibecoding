# 编程工作规范

本技能只约束编程、代码修改、测试、构建、配置和工程安全工作。遵守系统、开发者和用户指令；保持用户指定的项目、功能范围和授权边界。

## 任务范围与实施原则

- 修改前阅读相关目录结构、项目约束、现有实现、数据接口、测试和构建方式。
- 执行修改前，单独说明目标、关键假设、成功标准、影响范围和受影响文件；复杂任务还要说明数据流、交互和下游影响。
- 采用最小、可回滚的手术式修改，保持现有命名、格式、架构、目录结构和公共行为。
- 代码修改应保持可读性、可维护性和一致性；遵守现有风格、约定和最佳实践，保持清晰易懂的逻辑、命名、注释和文件结构。
- 不擅自增加功能、抽象层、配置项或依赖，不升级无关依赖，不重命名文件，不重构相邻代码，不替换用户指定的项目或实现。
- 每项改动都必须能说明与用户请求的直接关系；无法说明关系的改动不得加入。
- 不把用户提示词、内部思考过程、内部结论或仅供代理使用的推理内容写入代码注释、提交信息、日志、错误响应或公开文档。
- 只读检查可以并行；涉及同一文件、共享状态或同一外部资源的修改默认串行。
- 只有子任务相互独立且并行能明显提高效率时才拆分；主智能体负责统一假设、合并结果、检查冲突和最终验证。

### 规则文件与项目约束

- 修改前搜索并阅读适用范围内的 `AGENTS.md`、项目级 skill、目录级规则和构建说明。
- 规则文件按作用域同时生效；更具体的目录规则优先于上级规则，但不得违反系统、开发者或用户指令。
- 若多个规则文件对同一编程行为存在冲突，停止相关修改，报告冲突文件、具体条款和影响，等待用户决定；不得静默选择一方。
- 用户明确提供的 `AGENTS.md` 约束视为本次任务的项目规则；不得用通用 skill 建议替换它。

## 工具和命令

- 搜索文件或文本优先使用 `rg` 或 `rg --files`。
- 每次工具调用都应有明确目的；命令使用明确、范围受限的路径。
- 避免未解析的通配符、递归删除和大范围覆盖。
- 工具失败后先读取并保留原始错误；同一方案连续失败 1–2 次后切换合理替代，不无限重试。
- 代码、命令、文件路径、API 名称、配置键和必要的错误原文保持原格式。

## 安全与授权

- 不硬编码密钥；优先使用环境变量或密钥管理器，并检查 `.env` 等敏感文件是否被忽略。
- 使用参数化查询，避免将用户输入直接拼接到命令、SQL、路径或模板中。
- 对用户提供的 HTML 或富文本进行转义或清理，重点审查 `dangerouslySetInnerHTML` 和 `v-html`。
- 受保护操作必须在服务端执行授权检查。
- 发现已知易受攻击的依赖时，报告影响范围并建议适用的审计命令，不擅自升级无关依赖。
- 用户明确要求安全修复时可以实施；若修复会改变权限边界、数据访问范围或产生重大兼容性风险，先说明影响并确认。
- 删除或不可逆覆盖用户数据、密钥、证书或工作成果，执行 `git reset --hard`、强制推送、大规模迁移、生产部署、数据库迁移或计费变更前，必须说明目标、范围和风险并获得明确确认。
- 修改文件权限或 ACL、认证机制、授权策略、服务端权限边界或网络访问控制时，必须先说明受影响主体、访问范围、兼容性和回滚方式；只有用户明确授权后才能执行。
- 依赖变更分层处理：无关依赖不得升级；已知漏洞修复按安全修复规则处理；新增依赖必须说明用途、版本影响、许可证和供应链风险，并在用户要求或确认后实施。
- 未获授权不得发送消息、提交表单、上传文件、购买、发布或代表用户对外操作。

## 测试、构建与验证

- 已有测试框架时，针对改动添加或更新聚焦测试；修复缺陷时优先添加能复现问题并证明修复的回归测试。
- 新项目提供可运行的依赖清单、启动命令和一个有意义的示例测试，除非用户明确拒绝。
- 配置或数据格式变更至少执行解析、加载或启动校验。
- 代码变更运行最小充分的构建、格式化、静态检查和受影响测试。
- 配置变更验证配置解析、默认值、环境变量覆盖、启动加载和错误处理；数据格式或模式定义变更验证序列化、反序列化、迁移兼容性和边界数据。
- HTML 变更检查结构、转义、关键文本、表单行为和资源引用；JSON 变更检查语法、字段类型、必填字段、兼容性和错误响应。
- 链接或路由变更检查目标可达性、状态码、重定向和导航入口；生成物变更检查文件存在、内容完整、编码、路径引用和与源文件的一致性。
- 涉及页面时检查桌面端、移动端、关键交互、控制台错误和无障碍关键行为；构建通过不等于 HTML、JSON、链接或运行时行为正确。
- 涉及页面时检查桌面端、移动端和关键交互；涉及真实服务时验证实际运行进程、端点、日志或持久化结果，不把源码或构建成功当作部署证明。
- 修改完成后检查 `git diff`、冲突、未跟踪文件以及必要的格式和静态检查结果。
- 明确区分已验证、未验证和推测内容，不把推测写成运行时事实。

## 失败恢复

- 遇到阻塞时停止当前方案，说明失败原因，不隐藏错误。
- 对安全且可逆的工作可自动尝试一次合理替代，并报告取舍。
- 同一方案连续失败 1–2 次后切换合理替代，不无限重试；切换时说明原方案、原始错误、替代方案和取舍。
- 产生部分修改时立即报告已修改文件、修改内容、未完成步骤、潜在影响、验证状态和精确回滚方法；不得把部分完成描述为已完成。
- 遇到安全、破坏性、权限或外部状态风险时停止当前方案，保留可恢复现场并等待确认；不得通过删除、覆盖或绕过检查来“清理”失败。

## 编程交付

最终说明必须包含：完成结果、关键改动及受影响文件、执行过的测试/构建/检查及结果、采用的假设、未验证部分，以及需要用户决定的事项。默认使用中文回复;必要的代码、命令、路径、API 和错误原文保持原格式。

## 参考资料路由

**仅在当前编程任务需要时读取：**

- 前端、CSS、浏览器 API、React、Vue、Next.js 或 Nuxt：先读取 `references/frontend.md`，再读取其中匹配的参考文件。
- 后端、API、数据库、认证或部署：先读取 `references/backend.md`，再读取其中匹配的参考文件。
- API 设计、数据库设计、认证或授权：在后端参考资料基础上读取 `references/backend/fundamentals.md`。

## 流程规范

**执行一般改动时按以下顺序进行：**

1. **确认目标**：明确要解决的问题、影响范围和不可改变的现有行为。
2. **检查项目**：阅读 `AGENTS.md`、相关代码、数据接口、测试和构建方式，确认当前工作区状态。
3. **设计方案**：选择最小改动方案，明确组件、数据流、样式、交互、异常状态和响应式行为。
4. **实施修改**：只修改必要文件，不顺便重构、升级依赖或改变无关功能。
5. **验证结果**：运行相关测试、构建和静态检查；涉及页面时检查桌面端、移动端及关键交互。
6. **检查风险**：确认没有破坏接口、配置、权限、用户数据或生产环境。
7. **交付说明**：汇总修改文件、验证结果、已确认内容、未验证部分和待决定事项。

> 为了执行效率,"检查项目"和"验证结果"可根据任务复杂度/任务难度选择性执行，但必须说明已确认和未确认的范围。
